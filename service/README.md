# Paper proposal service

This local service is the boundary between the phone interface and a future user-owned trading agent.

## Durable trading ledger

`trading_ledger.mjs` defines the first version of the local SQLite lifecycle ledger. It stores immutable proposal terms, one decision per proposal, restart-safe submission idempotency keys, broker-order identities, and append-only lifecycle events. Run `npm run test:ledger` to verify persistence and duplicate protection.

The proposal-through-submission service path now writes to the ledger. On startup, unresolved proposals and their decisions are restored, successful preview and What-If gates are recovered, and a repeated submission uses its durable idempotency record instead of contacting IBKR again. If connectivity is lost after transmission begins, the attempt is marked `unknown` and another transmission is blocked until broker reconciliation determines what happened.

Read-only IBKR reconciliation collects balances, positions, open orders, and executions into a complete source snapshot. It runs every 5 seconds while orders are active, every 15 seconds while positions are open, and every 60 seconds while the account is quiet. Recognized application order references are linked back to the ledger; broker evidence resolves an otherwise unknown submission without retransmitting it. External/manual broker activity remains visible rather than being overwritten.

An optional, git-ignored `service/data/paper-transaction-history.json` holds manually reviewed historical Paper transaction movements for selected symbols. Its account value must use the same masked form returned by the read-only IBKR collector. The service checks that account label and shows whether the net share quantity agrees with the current broker position. A masked label alone is not unique account proof: the history never assigns app ownership or sale authority. A mismatch blocks otherwise exact ownership matching. Set `HISTORICAL_BROKER_EVIDENCE_PATH` for a different local file; do not commit personal statement data. Recheck the record after later broker trades, since it is a dated observation rather than an automatically refreshed feed.

For positions created before the SQLite ledger, generate an IBKR Paper Activity Flex Query with Trades → Execution, a 365-day window, `Include Audit Trail Fields: Yes`, and CSV output. It must cover the entire relevant trading period and contain the target symbols, `TradePrice`, `IBCommission`, `IBCommissionCurrency`, execution IDs and order references. Run `node service/import_paper_flex_report.mjs /path/to/report.csv` to validate the same-account executions, API-order flag, unique execution IDs and `trade-approval-…` order references, then store a minimal private summary at `service/data/paper-flex-attribution.json`. Run `node service/import_paper_flex_commissions.mjs /path/to/report.csv YYYY-MM-DD` to attach fees only where both execution ID and application order reference match the durable ledger. The commission import is idempotent, records the source digest and rejects ambiguity or conflicts. The service uses position attribution only when signed quantities exactly match the current broker position, broker average cost is present, and no observed external trade contradicts it. This bridge verifies legacy app origin and fees, not original approval details or protective-stop coverage. Any later quantity change without fresh attribution fails closed; do not commit the CSV or private summary. Set `PAPER_FLEX_EVIDENCE_PATH` only if storing the summary elsewhere.

## Alpaca research cache and scanner

Alpaca supplies the active U.S.-equity asset master and adjusted daily bars. The cache uses IEX by default; SIP is used only when explicitly configured and available to the account. `npm run market:refresh` removes non-tradable, OTC and obvious non-common-stock instruments, ranks the survivors by the latest completed session's dollar volume, stores the top 500 and roughly 430 calendar days of history in `data/market-cache.sqlite3`, and never stores credentials. A same-day daily bar is excluded until 16:15 New York time; malformed, future and weekend same-day bars fail closed. Every rebuilt cache records `completedThrough`, deletes previously stored bars atomically, and a scan refuses a legacy cache with no completion boundary. This deliberately delays early-close data rather than guessing that a session is complete. `npm run market:status` reports cache coverage; `npm run market:scan` evaluates the cached universe without contacting IBKR.

`service/volatile_stock_coverage.py SOURCE.csv OUTPUT_PREFIX` compares an external symbol list with the completed-data core and aggressive caches. It reports whether each symbol was observed, technically rejected or qualified for research and preserves every failed aggressive-lane check in JSON. The report is diagnostic only: listed implied volatility is not treated as direction, news or permission to trade.

Run `.venv-ibkr-10.49/bin/python service/aggressive_shadow_scanner.py refresh --symbols-csv /path/to/list.csv` to replace the durable imported symbol set and add every active, supported `Symbol` in that CSV to the isolated aggressive cache regardless of its top-1,500 IEX-volume rank. Later ordinary refreshes preserve that imported set. Imported names still pass the same completed-history, price, IEX venue-liquidity, ATR, momentum and relative-volume checks. The cache records imported names that are missing from the active asset master or unsupported instead of silently dropping them. Shadow v2 also reports 20-day realized volatility, 60-day maximum drawdown and the latest opening gap as diagnostics; they do not yet change eligibility or grant order authority.

Set `APCA_API_KEY_ID` and `APCA_API_SECRET_KEY` in the ignored `.env.local` file. The cache fails closed when credentials or data are unavailable. The free Alpaca plan may provide historical SIP bars when the request ends outside the restricted recent-data window; current feed access remains account-dependent.

`POST /shadow/scan` evaluates the local cache and stores the selected observation and its checks in `data/shadow-signals.json`. Repeating the same ruleset, symbol, and signal date is idempotent. IBKR remains the authority for the final bid/ask, paper account, What-If validation and execution.

`GET /shadow/signals` returns the durable shadow ledger. Shadow records always include `orderSubmissionAllowed: false`; they are not accepted by the approval or paper-order routes.

## Stock news context

The separate higher-volatility research lane runs with `npm run market:aggressive:refresh`, `npm run market:aggressive:scan`, and `npm run market:aggressive:status`. It uses `data/aggressive-market-cache.sqlite3` and the authenticated read-only `GET /shadow/aggressive` endpoint. Its top-1,500-plus-eligible-watchlist universe and volatility/relative-volume thresholds are experimental. Price direction, momentum, relative volume and liquidity form the signal; a news catalyst is optional context and its absence is not a rejection. Output is **not** yet an actionable recommendation because consolidated liquidity, a live spread, portfolio sizing and fresh broker validation are still missing. The existing 500-stock recommendation and IBKR submission paths are unchanged. Run `python -m unittest discover -s service -p test_aggressive_shadow_scanner.py -v` for isolated tests.

`intraday_shadow_evaluator.py` is a provider-free, research-only evaluator for immutable intraday observations. It checks observation/quote freshness, regular-session state, halts, coherent prices, day momentum, opening gaps, relative volume, session dollar volume and spread, returning all failures rather than stopping at the first one. It cannot fetch data, persist observations, create proposals, size trades or call a broker. All thresholds are proposed test variables. `test_intraday_shadow_evaluator.py` includes a BMNR-like move and fail-closed stale, future, crossed and incomplete snapshots.

`intraday_shadow_journal.py` adds append-only SQLite research evidence without connecting a provider. It requires data-source and consolidated/single-venue/unknown volume provenance, stores passing, failing and incomplete evaluations, deduplicates exact repeats and blocks row updates/deletes. Replay is chronological and refuses to reinterpret an unknown historical ruleset. The journal does not make the evaluator actionable and is not connected to the application API or broker.

`intraday_volume_profile.py` builds a 390-point expected cumulative-volume curve from the median of the latest 20–30 complete prior regular sessions. It excludes the current session, requires at least 380 observed bars plus both boundary minutes, carries zero-trade missing minutes as zero volume, rejects duplicates and records an exact input digest. `intraday_volume_profile_job.py` fetches read-only Alpaca `1Min` pages and atomically writes the git-ignored research artifact; run it with `npm run market:intraday:profiles -- SYMBOL [SYMBOL ...]`. The artifact explicitly retains IEX `single_venue` or SIP `consolidated` provenance and grants no recommendation or order authority.

The production-shaped refresh uses `npm run market:intraday:refresh-profiles`. It reads the existing artifact as the frozen universe/feed contract, rebuilds every profile, requires identical volume/range session dates, refuses a per-symbol session regression and replaces the live JSON only after the complete candidate validates. Partial failure preserves the previous artifact byte-for-byte. `ops/com.tradeapproval.intraday-profile-refresh.plist` runs the non-overlapping refresh at 8:45 a.m. local time each weekday so the current market day cannot enter its own baseline. The refresh is research-only and cannot change recommendations or orders.

`intraday_price_signals.py` adds a 390-point median cumulative-range profile plus as-known movement diagnostics: 5/15/60-minute returns, previous-five-minute momentum, acceleration, VWAP distance, range expansion, session-high pullback, recent close location and positive-bar share. It requires at least 60 minutes of exact history and rejects stale, future, duplicate, cross-session or incoherent bars. These values are explanatory research inputs only; the module does not rank candidates, create cards, size trades or call a broker.

`intraday_opportunity_score.py` combines only complete upstream gate and price evidence into a transparent 100-point long-direction shadow score: relative volume 25, multi-horizon momentum 25, acceleration 10, VWAP position 10, range expansion 15 and recent path quality 15. Every component returns its exact input, points, cap and explanation. Failed freshness, halt, price coherence, day movement, liquidity or spread gates block scoring; symbol/time/provenance mismatches and missing metrics also block it. The weights and 60/75 bands are uncalibrated forward-test hypotheses, not evidence of profit, and all outputs deny recommendation and order authority.

`nasdaq_halt_status.py` reads the official Nasdaq Trader current-halts RSS feed over a fixed HTTPS host, once per scan. It enforces a two-minute publication-age limit, response-size and XML-safety limits, exact symbols, Eastern halt/resumption times and explicit source provenance. `intraday_safety_filters.py` then separates market-quality failures from portfolio conflicts across halt state, spread, liquidity, profile completeness, overextension, extreme range, broken pullback, account freshness, position capacity, projected exposure, daily loss and buying power. IEX remains acceptable only for labeled shadow collection; consolidated data and calibrated forward results remain promotion blockers. Review and satisfy Nasdaq feed terms before distributing feed-derived data commercially.

`intraday_shadow_capture.py` is the read-only scheduled orchestration boundary. During regular weekday market hours it loads frozen profiles, fetches labeled Alpaca IEX evidence and one Nasdaq halt snapshot, evaluates every configured symbol, calculates price diagnostics and score where eligible, applies safety filters and records the complete result. `intraday_capture_journal.py` atomically preserves every run and every `PASS`, `REJECTED` or `INCOMPLETE` record in append-only SQLite; exact reruns are idempotent and conflicting reruns fail. Valid observations also enter `intraday_shadow_journal.py` for deterministic outcome replay. Run once with `npm run market:intraday:capture` and inspect the latest run with `npm run market:intraday:status`. The installed `ops/com.tradeapproval.intraday-shadow.plist` invokes `ops/run-intraday-shadow.sh` every five minutes with a non-overlap lock and performs no network work outside market hours. Portfolio context remains deliberately unavailable until a fresh read-only broker adapter is connected, and no component can create a recommendation or order.

`intraday_forward_outcomes.py` settles exact 5- and 30-minute windows from the immutable capture timeline. A target must be the first same-symbol observation at or after the horizon and no more than two minutes late. Missing mature windows are permanently `INCOMPLETE`; horizons after the regular-session close are not expected. Complete results retain both record identities, the original pass/reject status, score and safety evidence, raw last-price return and an explicitly hypothetical cost estimate using entry ask, exit bid, two basis points of slippage per leg and one basis point of round-trip fees. The separate SQLite journal is append-only, conflict-safe and summarized by cohort with a 20-distinct-session review gate. These are observation outcomes, not fills or expected-profit claims, and grant no recommendation or order authority.

`intraday_provider_contract.py` joins a normalized Alpaca snapshot to independently sourced expected-volume and halt context. It requires exact symbol identity, context no more than 60 seconds old, at least 20 historical profile sessions, a known halt state and explicit IEX/SIP scope. It derives regular-session state in New York time and never upgrades IEX single-venue evidence to consolidated. The current account can read IEX but not SIP, so this contract remains shadow-only and is not connected to the recommendation queue or broker.

`intraday_shadow_replay.py` imports newline-delimited recorded observations only after validating the complete file envelope and provenance. Reimports are idempotent through the journal. Its research report chooses the first eligible observation for each symbol and New York market-session date, then measures exact 5-minute and 30-minute observation windows, last-observed return, and favorable/adverse excursion. Missing windows remain incomplete; it never substitutes a distant price. These are reference-price observations—not fills—and exclude spread, slippage, fees, tax and market impact. The report cannot establish profitability and has no order authority.

`macro_event_bias.py` is the first pure component for a macro/news-and-volatility research lane. Caller-supplied evidence must identify a supported event type, timestamp, primary-source verification or two independent sources, surprise magnitude and confidence; it must also state the symbol's directional theme exposure. A fresh, non-halted quote then has to confirm direction, price movement, relative volume, an explicit ATR band and an acceptable spread. The result is a `LONG` or `AVOID_OR_EXIT` research bias with a versioned score, never a proposal or order. These thresholds are hypotheses for forward testing, not evidence of an edge.

`macro_event_journal.py` stores the exact event, source records, exposure-map version/rationale, market-data provenance, reaction snapshot and evaluation in append-only SQLite. Exact repeats are idempotent; source URLs/timestamps, event revisions, exposure provenance, market-data source and volume scope are mandatory. Corrections append a new revision instead of rewriting history. Database triggers prohibit updates and deletes, while replay refuses to reinterpret retired rulesets. It has no network or broker authority.

`macro_event_sources.py` provides a fixed allowlist and provider-neutral normalization contract for the Federal Reserve monetary-policy RSS feed, BLS Employment Situation RSS, BLS CPI RSS and the documented BLS release-calendar ICS. Responses are size/time bounded; redirected and item links must remain on the official host; unsafe/malformed XML and incomplete records are rejected. Stable source identity is separate from a content fingerprint so corrected feed entries can be detected without losing lineage. Feed items are explicitly `IDENTIFIED_NOT_SCORED`: official releases do not supply the market-consensus forecast needed to calculate surprise. A September 20 live read-only smoke check succeeded for all three RSS feeds. The BLS ICS endpoint returned HTTP 403 to an automated GET, so scheduling must remain unavailable until an approved reliable retrieval method exists.

`macro_consensus.py` defines a provider-neutral consensus record and a provisional Trading Economics calendar adapter. It accepts only exact-time, medium/high-importance U.S. events with stable IDs, update timestamps, official-source metadata and numeric value fields requested from the provider. Scheduled, released-without-consensus and released-with-consensus states remain distinct; missing actual or consensus values never become zero. Raw surprise retains the indicator's units. A bounded standardized surprise is calculated only from at least 12 strictly earlier observations of the same series, excluding future and cross-series records. The API key is header-only and date ranges are capped at 31 days. No subscription has been purchased, licensing has not been approved, and this adapter is not connected to the journal or recommendation queue.

`macro_exposure_map.py` provides an append-only registry for reviewed theme-to-symbol relationships. Every entry requires a bounded direction and strength, effective interval, substantive rationale, and timestamped HTTPS evidence classified as a filing, company report, official dataset, index methodology or regulator publication. Drafts, duplicate pairs, future evidence, invalid intervals and changes under an existing version are rejected. New reviewed versions may explicitly supersede known versions; older maps remain available for deterministic replay. Resolution is always by an explicit map version and as-of timestamp. No real company mappings ship yet, and the registry never infers exposure from a ticker or headline.

`macro_event_joiner.py` assembles official releases, scored consensus records, reviewed event crosswalks, active exposure mappings and post-release market reactions into the exact evidence contract used by the macro journal. Identity, review, timestamp, standardized-surprise history, mapping and reaction gates all fail closed. Similar names or dates never create an inferred match. The joiner is pure and has no scheduler, provider, proposal or order authority.

`macro_capture_scheduler.py` is a durable provider-neutral forward-capture schedule. Plans must be created before the release and pin event/link/map versions plus symbols. It creates a five-minute baseline, one release capture and per-symbol 1-, 5- and 30-minute reaction tasks. Claims are transactional and restart-safe; late tasks become `MISSED`, completed observations must fall inside the task window and all transitions are append-only audited. It does not run a clock, fetch data or affect recommendations or orders.

`macro_capture_worker.py` is an explicitly invoked read-only task runner. Provider implementations are injected behind separate release and market capture methods. Release records require primary-source and consensus identities; market records require coherent prices, volume baseline, prior close, ATR, halt state and data/volume provenance. Invalid evidence and provider exceptions are saved only as sanitized failures. Process death leaves a task claimed and visible. No production provider, timer, secret, recommendation or broker path is included.

Stage 7 hardening requires exact symbol, scheduled-event, event-link-version and exposure-map-version matches. A claimed task interrupted by process death can receive one immutable supervised disposition without becoming pending again. See `MACRO_RESEARCH_PLAN.md` for the gated stages through provider integration, forward evaluation and any later promotion review.

`macro_provider_adapters.py` begins Stage 8 with a bounded Alpaca snapshot client and a provider-composition adapter. It labels IEX as single-venue and SIP as consolidated, rejects delayed data for forward capture, blocks redirects, limits time/bytes and sanitizes provider failures. A market snapshot must be joined with a named context source for fresh halt state, expected time-of-day volume and ATR; missing context fails closed. Official and consensus readers remain injected so Stage 9's reviewed crosswalk can select exact identities. See `MACRO_PROVIDER_REVIEW.md`; Trading Economics and the missing market-context source remain unapproved/unconfigured.

`macro_research_universe.py` validates the frozen Stage 9 research universe. It requires separately identified curation and later source-verification passes, exact official series and HTTPS sources, documented limitations, sufficiently liquid symbols and a matching reviewed exposure entry for every study. A blocked study cannot contain a guessed consensus ID; an active study requires an approved exact consensus ID and reviewed crosswalk. The first universe contains BLS payrolls/JPM and CPI/Home Depot, but intentionally exposes zero registerable studies until the consensus dependency is resolved.

`macro_forward_pilot.py` is the Stage 10 supervisory boundary. It checks active-study status, official/consensus/market/context health, worker identity, one-second clock synchronization and pre-baseline timing before allowing registration. Its report preserves task and audit timelines, latency, data sources, all terminal/incomplete counts, unresolved claims and byte-canonical replay equivalence under a deterministic digest. The recorded five-task rehearsal is complete, but the real universe fails preflight and no real event has been registered.

`macro_outcome_analysis.py` implements the Stage 11 research-only report. It admits only complete, deterministic `REAL_FORWARD` observations and keeps rehearsals, failures, corrections and missing data visible as exclusions. It compares fixed 1-, 5- and 30-minute after-cost returns with exact matched no-event sessions, benchmark and cash references; preserves excursions, drawdown, volume, volatility regime, momentum context and lateness; and blocks promotion on duplicate identities, chronological leakage, mixed versions or inadequate samples. The frozen decision rule is documented in `MACRO_OUTCOME_CONTROLS.md`. No real observation is currently eligible.

`macro_shadow_ranking.py` implements the isolated Stage 12 comparison. It applies at most a five-point macro adjustment to candidates that already pass every hard gate, records baseline and shadow orders from one input digest, and rejects future-dated macro evidence. Its chronological forward report requires identical baseline/shadow inputs and applies predeclared degradation, drawdown and operational rollback thresholds. A real run requires Stage 11 promotion; recorded fixtures have no recommendation or order authority. See `MACRO_SHADOW_RANKING.md`.

`macro_promotion_review.py` implements the Stage 13 release boundary. It evaluates the complete rights, performance, reliability, security, policy, monitoring, rollback, integration and broker/reconciliation dossier; records one attributable immutable decision per assessment; and can derive only a default-off bounded-ranking manifest from a valid approval. It cannot activate the flag, change the production queue or grant broker authority. No real promotion decision currently exists. See `MACRO_PROMOTION_REVIEW.md`.

`GET /research/news?symbol=AAPL` provides stock-specific Benzinga headlines through Alpaca using the existing server-side `APCA_API_KEY_ID` and `APCA_API_SECRET_KEY`. Up to ten normalized headlines are displayed from one page of up to 50 records covering seven days. Publication/update times and original links are preserved; full article bodies are not requested. Pagination or rejected records produce an explicit partial result, not a claim of complete coverage. Feed latency is unverified.

The same response includes `catalystResearch`, a deterministic headline-only classification for earnings/guidance, FDA/clinical events, financing/dilution, M&A, contracts/partnerships, regulation/legal events, analyst actions and macro/industry themes. Each match preserves evidence, affected symbols, publication time, lexical direction, bounded classification confidence, window-relative novelty and source quality. Predictive confidence is always null. The classifier is research-only, treats the aggregator as secondary evidence and cannot adjust a rank or authorize an order.

`options_volatility_research.py` defines the provider-neutral options-volatility research contract. A complete evaluation requires a fresh consolidated OPRA snapshot, coherent option contracts across at least two expirations, IV and delta, bid/ask spreads, volume, open interest, 20-session realized volatility, known-event distance and at least 60 point-in-time underlying-IV observations. It reports ATM IV, IV percentile, IV-minus-realized spread, term structure, 25-delta skew and liquidity diagnostics. It never ranks a stock, proposes an option or submits an order. A read-only entitlement check on September 21 found that current Alpaca credentials can request indicative quotes but not OPRA, and the sampled indicative response had no usable IV or Greeks. No provider subscription or production connection is authorized.

`shadow_strategy_comparison.py` evaluates the baseline and volatile-growth lanes on the same completed daily signal dates without exposing future bars to either evaluator. It enters at the next session open, compares equal-weight top-five lane outcomes at 1, 5 and 10 sessions, applies an explicit round-trip cost assumption and reports QQQ-relative results, uncertainty and diagnostic drawdown. `run_shadow_strategy_comparison.py` reads the two local caches and writes a reproducible JSON report. Because those caches contain today's selected universes rather than historical point-in-time membership, generated reports are retrospective diagnostics with promotion disabled. Historical headline catalysts are also excluded until an immutable as-known archive exists.

`daily_evidence_capture.py` stores point-in-time forward evidence in the ignored `service/data/daily-forward-evidence.sqlite3`. It requires matching completed-session boundaries, freezes the full baseline and shadow universes plus the frozen directional-volume treatment and every pass/fail evaluation, and rejects a changed second capture for the same session. Later runs append immutable 1-, 5- and 10-session outcomes only when exact future bars exist. The version-4 evidence schema measures **every** observed candidate, including filtered candidates, from the next session's open through each horizon. It preserves entry/exit prices, gross and cost-adjusted return, maximum favorable/adverse excursion, and exact-window nominal cash and QQQ benchmarks. QQQ receives the same round-trip cost assumption; cash is explicitly zero nominal return with no trade cost. These are research counterfactuals—not fills or recommendations. A flawed run is preserved and excluded through one append-only invalidation; it is never rewritten or deleted, and invalidated runs cannot receive new outcomes. `npm run market:evidence:capture` captures and attaches available results; `npm run market:evidence:status` reports collection progress; `npm run market:evidence:report` compares eligible and filtered cohorts by lane, horizon, rejection reason, cash and QQQ; `python service/run_daily_evidence.py invalidate RUN_ID REASON` records an invalidation; `npm run market:daily` performs both refreshes and then captures. The repository includes the host timer definition but does not silently install it on another machine, and no capture or report can affect recommendations or orders.

Schema version 4 also appends snapshots of the durable application ledger. Exact signal date, symbol and source lane are required before a proposal is attributed to a forward-evidence run. The report separates approved, denied, expired, blocked, undecided and replaced/unselected proposals; submission and broker-entry states; proposed limit versus observed average fill; commission coverage; and incomplete reasons. Older proposals without a matching frozen run stay visible but unlinked. Ledger snapshots are append-only so later broker evidence creates a new observation rather than rewriting what was previously known.

`proposal_evidence_identity.mjs` resolves a newly generated proposal's date, lane, symbol and ruleset against the active immutable evidence database before ledger persistence. The proposal records the exact run ID and resolution status when available. Lifecycle capture repeats the lookup and refuses a claimed run or ruleset mismatch. Missing or pre-collector evidence remains explicitly unlinked; no historical identity is inferred and no broker authority comes from a match.

`portfolio_performance.py` builds a broker-grounded Paper equity curve from application-owned filled entries and exits only. It reports a daily gross/net scorecard, realized and unrealized P/L, deployed exposure, dollar and sleeve turnover, maximum gross drawdown, open positions, proposal-relative execution slippage and same-window nominal cash/QQQ comparisons. Positive slippage is worse than the frozen proposed price. It includes both fully invested QQQ and a dynamic QQQ alternative scaled to recorded daily ending exposure, with 20 basis points applied pro rata to allocation changes. That ending-exposure method is an explicit approximation of intraday opportunity cost. The annualized information ratio is withheld until 20 sessions exist. Live and external activity are excluded. Net equity, return and net benchmark excess remain null until every included execution has commission evidence. Missing daily marks make the report incomplete instead of silently carrying a price forward.

`npm run market:evidence:readiness` reports progress toward the frozen 20-distinct-session gate separately for 1-, 5- and 10-session outcomes, requires matching QQQ windows, and reports matched proposal-session progress independently. The weekday collector logs this readiness after every successful refresh and capture. Reaching the target permits review; it does not automatically change a rule or enable trading.

`npm run market:evidence:archive-performance` generates the current broker-grounded scorecard and appends its canonical payload to the ignored `service/data/performance-report-archive.sqlite3`. Exact reruns are idempotent by SHA-256; later fee or evidence revisions are preserved as separate immutable rows. Database triggers block update and delete. The scheduled collector runs this after evidence capture and before readiness reporting.

`directional_volume_experiment.py` freezes one research-only treatment: all higher-volatility gates remain unchanged except relative volume becomes ranking context instead of a hard veto. The evidence report selects the top five control and treatment names deterministically, admits only sessions with complete paired outcomes, and reports after-cost return differences, descriptive 95% bounds and additional maximum drawdown. Twenty distinct paired sessions are required at each horizon. The September 23 rehearsal (80 control versus 262 treatment eligible names) is diagnostic only and is not stored as promotion evidence. The treatment cannot create recommendations or orders.

The installed macOS LaunchAgent uses `ops/com.tradeapproval.daily-evidence.plist` and runs `ops/run-daily-evidence.zsh` at 4:30 PM local time Monday through Friday. It sources `.env.local`, takes a non-overlapping local lock, captures evidence, archives performance, reports readiness and writes the ignored `service/data/daily-evidence-launchd.log`. A different refresh payload for an already frozen completed session is reported as a preservation warning; the original snapshot remains immutable and outcome attachment still proceeds. The Mac must be awake and logged in for this user LaunchAgent to run.

The route uses existing app authentication. A bounded 60-second in-memory cache, concurrent-request coalescing, an eight-request concurrency cap, time/size limits and Retry-After handling protect the service. API secrets and raw upstream errors never enter responses. Preview Mode makes no news requests. News cannot affect scan eligibility, proposal prices, approval or submission. Run `node --test service/stock_news.test.mjs` for fixture tests.

## SEC EDGAR research source

The service uses Alpaca for bulk historical research, IBKR for current quote/account/execution data, and the official SEC EDGAR APIs for recent 10-K, 10-Q and 8-K filing metadata plus standardized XBRL revenue and net-income facts. Set `SEC_USER_AGENT` to a descriptive application name and contact email before enabling requests. SEC research is cached for 15 minutes, attached to proposals as context, and is explicitly marked `researchOnly`; it does not affect eligibility, sizing, prices, approvals, or order submission.

`GET /research/sec?symbol=NVDA` returns the normalized research record for a supported U.S. company. ETFs in the scanner universe are intentionally excluded.

Risk calculations live under `service/risk/`. Components have no network or broker side effects and return a versioned structured result. `equity-observed-market-risk-v1` currently combines volatility, overnight-gap, and historical-liquidity components. Complete trade risk remains null until entry, stop, quantity, portfolio, current spread, and event data are available.

`intraday_portfolio_context.py` converts one complete, fresh, read-only TWS Paper reconciliation snapshot into projected intraday research constraints. It aggregates repeated broker position rows by symbol, checks position capacity, proposed symbol and reviewed exposure-bucket concentration, daily loss and buying power. `data/intraday-sector-registry.json` supplies versioned explicit classifications with source links; an unknown held or candidate symbol fails closed. One broker snapshot is reused across the full symbol cycle. Missing, stale, Live or writable evidence fails closed, and the adapter has no recommendation or order authority.

It deliberately cannot submit live orders. Approved proposals receive an HMAC-signed, single-use receipt that binds the approval to an exact paper account, symbol, buy direction, quantity, order type, maximum entry price, protective stop, profit target, automatic-exit policy, and short expiration.

```sh
APPROVAL_SIGNING_SECRET="replace-for-local-testing" node service/server.mjs
```

- `POST /proposals/demo`
- `POST /proposals/:id/decision` with `{ "decision": "approved" }` or `denied`
- `POST /orders/preview` with a signed approval token; validates and previews but cannot submit
- `POST /orders/what-if` runs IBKR's broker-side pre-trade check only when explicitly enabled; it forces `whatIf=true`. IBKR requires `transmit=true` for What-If validation, but does not execute What-If orders.
- `POST /orders/submit-paper` submits only after a signed recommendation approval, preview, What-If, a fresh quote/account check, and an unused approval. The symbol must match the current server-approved Alpaca-universe proposal. It accepts only a BUY of 1–5 whole shares and at most $1,500 notional in the IBKR paper account. The adapter submits a coordinated bracket: DAY limit buy, attached GTC profit-taking limit sell, and attached GTC protective stop sell. No standalone, arbitrary-symbol, or short sell order is accepted.
- `POST /pause` with `{ "paused": true }`

The adapter accepts only verified receipts whose `environment` is `paper`, refreshes account and quote data, and rejects altered, expired, duplicate, over-limit, or invalid-bracket orders.

Automatic Paper strategy exits are currently disabled by a code-level release hold in both the service worker and the direct paper-exit adapter; `IBKR_ENABLE_AUTOMATIC_SELLS=true` cannot bypass it. The former cancel-protective-order-then-submit-sale path is blocked before broker connection. Its quote gate requires IBKR live data type 1, valid bid/ask within the configured spread, and both local quote callbacks within five seconds. Callback arrival time is not an exchange timestamp. A successful scanner run must also contain a complete held-symbol evaluation for the exact expected prior weekday session; stale, missing and errored results fail closed (exchange holidays are not yet modeled). Delayed type 3 data observed after the 2026-09-18 market open and the missing production broker modification/acknowledgement lifecycle are independent blockers. Existing broker-side stops and targets are separate from this disabled worker.

`protected_exit_lifecycle.mjs` is a credential-free simulator stage for replacing an existing bracket target while leaving its stop in place. It emits one descriptive intent, waits for broker-observed order terms, and never retransmits an uncertain request after restart. Rejection, partial fill, oversize stop, competing sell, disconnect and ambiguous closure fail closed. The deterministic broker models modification acknowledgements for tests; there is no IBKR modification adapter, durable production outbox, confirmed sibling rebalancing or permission to enable automatic selling. The account's API quote still returns warning 2186 after acknowledgement, subscriber classification and TWS restart.

`protected_exit_outbox.mjs` adds local SQLite persistence for those simulator intents. It saves immutable terms, permits one unresolved request per account/symbol, and commits a one-time dispatch claim before returning a descriptive command. Claim requires a new complete Paper broker snapshot; a crash after claim has an unknown transport outcome and cannot be retried without broker evidence. A separate IBKR adapter and service-worker integration have **not** been implemented. Run `node --test service/protected_exit_outbox.test.mjs` to exercise crash windows and read-only recovery.

The read-only ownership check requires the total linked active stop quantity to equal the current strategy-owned position. Partial coverage is `partial`; excess coverage is `overcovered` rather than safe. Neither passes the exit gate or strategy-capacity check. Simulated partial-exit tests intentionally leave an oversized sibling stop to verify that the app detects the hazard; actual IBKR bracket rebalancing must be observed separately.

## Verify the local IBKR paper connection

Keep TWS open, logged into Paper Trading, with API socket clients enabled on port
`7497`. Read-Only API may stay enabled for connection testing and must be disabled
only when intentionally testing paper submission. Then run:

```sh
.venv-ibkr-10.49/bin/python service/ibkr_readonly_check.py
```

This checker connects only to localhost and contains no order-placement code.

To make the read-only broker snapshot available to Expo Go on the same trusted
Wi-Fi network, run `npm run service:phone`. The service remains paper-only and
the IBKR connection itself stays restricted to localhost. Network requests must
also provide the private token stored in the ignored `.env.local` file.
